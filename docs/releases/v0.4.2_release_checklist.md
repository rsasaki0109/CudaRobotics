# v0.4.2 Release Checklist

Patch release for the v0.4.1 Docker `cudanav` exit hang. Tags and published assets
are immutable; a failed published artifact requires another patch release, not
a moved tag.

## Target and local gates

- Base: clean `master` containing the Docker `cudanav` shutdown fix; tag `v0.4.2`;
  Python and ROS 2 version `0.4.2`.
- Notes: [`v0.4.2_notes.md`](v0.4.2_notes.md).
- Keep `release_readiness.published_version`, published-wheel onboarding and the
  GHCR image reference at their current values until v0.4.2 assets and the
  image are actually public.

```bash
python scripts/test_version_consistency.py
python scripts/validate_v1_support_matrix.py
python scripts/test_python_core_sync.py
python scripts/check_docker_build_context.py
python -m pytest python/tests -q
git diff --check
```

## Exact-commit remote gates

Require successful runs at the same clean target commit:

- `.github/workflows/build.yml`
- `.github/workflows/python-package.yml`
- `.github/workflows/ros2_cuda_mppi.yml`
- `.github/workflows/repo-checks.yml`

Download `cudarobotics-manylinux-wheels` into a clean staging directory together
with a freshly built sdist, then verify from a fresh clone of the tag:

```bash
python scripts/verify_python_release_artifacts.py \
  --dist-dir build/release_v0.4.2/publish \
  --json build/release_v0.4.2/python_artifacts.json --require-clean
```

Require the 0.4.2 sdist and CPython 3.10 / 3.12 manylinux wheels, all bound to
the target source provenance. Record SHA-256 and size before upload.

## Publish only after gates pass

1. Create annotated `v0.4.2` at the validated commit.
2. Push the tag and require the tag-triggered `docker-image` workflow to pass,
   including its build-context check and in-image package verification. On a
   physical GPU, `docker run --gpus all <image> cudanav` must print a passing
   summary and exit 0 without manual interruption.
3. Dispatch the Python package workflow on the tag, verify the wheels as above
   and create the GitHub release from the notes with the verified files and
   `SHA256SUMS`.
4. Re-download assets into a new directory, verify byte counts and SHA-256,
   and re-run the archive verifier.
5. Only then advance published-version declarations, wheel onboarding and the
   GHCR image reference to v0.4.2 in a follow-up docs commit, and redeploy
   Pages from `master`.

## Recorded outcome

- Build, Python package, ROS 2 CUDA MPPI, repository checks and docs deploy
  passed on `c8c2095`; the tag-triggered Docker workflow and the tag-dispatched
  Python package workflow passed.
- The exact-tag sdist and cp310/cp312 manylinux wheels were verified in a fresh
  `v0.4.2` clone, published with `SHA256SUMS` and the artifact manifest, then
  re-downloaded and re-verified. Their SHA-256 values match the CI manifest.
- The published image (`sha256:a7a43927109e…`) passed the `wall_gap`
  controller benchmark on a physical GPU. Its `cudanav` mode printed a passing
  summary (`smoke_pass: true`, zero collisions) and exited 0 after 44 s
  without manual interruption; every launched node stopped on SIGINT, so the
  TERM/KILL fallback was not used.
