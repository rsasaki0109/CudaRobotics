# v0.4.0 - Measured GPU Robotics and Browser Labs

CudaRobotics v0.4.0 combines the native CUDA/ROS 2 stack with interactive,
device-local browser experiments that make CPU/GPU trade-offs inspectable.
Python and ROS 2 source packages use version 0.4.0. This is a pre-1.0 release;
the separate v1.0 support contract is not declared ready by this release.

## Highlights

- Browser MPPI Lab: seeded CPU/WebGPU rollout comparisons, four workload sizes,
  complete cold-start plan timing, stage breakdowns and output/command checks.
- Matched-budget MPPI missions: per-backend P90 count selection, three seeds,
  side-by-side paths, recorded distance and explicit deadline stops. Late plans
  finish computing but are discarded before motion; this is not real-time
  preemption or a guarantee that the GPU improves mission outcomes.
- Navigation Workbench: editable maps, clearance-aware routing, pallet
  replanning and map-size comparisons. Exact CPU and GPU distance transforms
  can be compared with the reference GPU implementation, including route checks.
- Particle Storm: interactive particle localization with seeded CPU/WebGPU
  comparisons and explicit GPU-unavailable behavior.
- Native KISS-ICP host-pipeline improvements, including exact normal scheduling,
  spatial queries, incremental map-normal maintenance and allocation reuse.
- A simplified GitHub Pages entry point, replayable comparison JSON, and
  additional browser reference and shader-validation coverage.

## Try the browser demos

- [MPPI Lab](https://rsasaki0109.github.io/CudaRobotics/docs/demo/)
- [Navigation Workbench](https://rsasaki0109.github.io/CudaRobotics/docs/navigation/)
- [Particle Storm](https://rsasaki0109.github.io/CudaRobotics/docs/particles/)

The browser demos use WebGPU and JavaScript, **not CUDA running in a browser**.
They run locally without a backend server. CPU wins, unavailable GPUs, output
mismatches, blocked routes and deadline misses are retained rather than hidden.
Measured browser ratios are not native CUDA/C++ performance claims.

## Python and ROS 2

### Staged availability

At the maintainer's request, the source tag and GitHub release are published
after local verification without waiting for queued GitHub-hosted CI. This is
the first stage of the normal release, not a claim that all distribution
artifacts are already available.

- The tagged Python and ROS 2 sources declare version 0.4.0.
- The Python 0.4.0 source distribution is built locally and attached after
  archive/provenance verification, including all 40 packaged source hashes.
- CPython 3.10 / 3.12 manylinux wheels are pending remote build and independent
  archive verification. No old binary is relabeled 0.4.0.
- The tag triggers the Docker workflow; a usable v0.4.0 image is not claimed
  until that workflow succeeds.
- The published-wheel installer and published-binary documentation remain at
  v0.3.0 until verified v0.4.0 wheels are attached. Repository/Pages source
  publication and native binary availability are separate statuses.
- Local Windows checks do not substitute for Linux wheel or ROS 2 Jazzy builds,
  and no new native physical-GPU validation is implied.

The Python distribution targets Linux x86_64. Once verified 0.4.0 wheels are
attached, select the file matching CPython 3.10 or 3.12:

```bash
python -m pip install ./cudarobotics-0.4.0-*.whl
```

Building the Python sources requires CUDA Toolkit 12 or newer and CMake
3.18 or newer. GPU execution requires a compatible NVIDIA driver. ROS 2 packages
target Jazzy / Ubuntu 24.04 with CUDA 12.6. The Colab notebook in this source
release is pinned to the immutable `v0.4.0` tag.

The attached source distribution can be built with:

```bash
python -m pip install ./cudarobotics-0.4.0.tar.gz
```

## Verification and limitations

Completion of binary distribution still requires exact-commit Build,
Python-package, ROS 2 and systems-paper workflows, plus browser repository
checks and Pages deployment. These workflows may remain queued at initial
source publication. Python archives and commit-bound evidence must be
independently validated before upload and re-downloaded for integrity checks.
The actual Docker outcome is recorded separately. A local verification report
lists exactly what ran; missing checks are not reported as successful.

Browser timings include the transfers and host work described by each panel;
GPU kernel utilization is not inferred from wall-time shares. Three deterministic
mission trials are not a reliability estimate or continuous collision proof.
Existing partial or negative native/real-dataset evidence is not promoted to a
successful result by changing the release version. New native physical-GPU
validation is reported only when that validation has actually run.
