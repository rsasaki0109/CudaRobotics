# v0.4.0 Release Checklist

This checklist gates the normal Python / ROS 2 / Docker release, not a
browser-only source snapshot. Tags and published assets are immutable. A failed
published artifact requires a patch release, not a moved tag.

## Maintainer-authorized staged publication

The maintainer authorized proceeding when local checks pass rather than waiting
for GitHub-hosted CI. Under this exception, publish the immutable source tag and
GitHub release with a local verification report and explicit pending-artifact
warnings. Do not claim that Linux wheels, the Python sdist, ROS 2 CI or Docker
verification succeeded. Do not relabel old binaries or attach unverifiable
artifacts. Keep the exact-tag-commit workflows running, and complete the binary
publication steps below only after their artifacts are actually validated.
Published-wheel onboarding stays at 0.3.0 until new binaries are available.

## Target and local gates

- Base: clean `master`; tag `v0.4.0`; Python and ROS 2 version `0.4.0`.
- Notes: [`v0.4.0_notes.md`](v0.4.0_notes.md).
- Keep `release_readiness.published_version` and published-wheel onboarding at
  `0.3.0` until the new release and assets are actually public.
- Validate source versions, the support matrix, Python bundled-core provenance,
  Python package tests, all browser reference tests and WebGPU shaders.
- Previously run local browser/device checks are supporting development checks,
  not substitutes for exact-commit release CI or native physical-GPU evidence.

```bash
python scripts/test_version_consistency.py
python scripts/validate_v1_support_matrix.py
python scripts/test_python_core_sync.py
python -m pytest python/tests -q
git diff --check
```

## Exact-commit remote gates

Require successful runs at the same clean target commit:

- `.github/workflows/build.yml`
- `.github/workflows/python-package.yml`
- `.github/workflows/ros2_cuda_mppi.yml`
- `.github/workflows/systems-paper.yml`
- `.github/workflows/repo-checks.yml`
- `.github/workflows/docs-deploy.yml`

Dispatch workflows not automatically triggered by the source change. Download
the Build, Python and ROS attestations and systems-paper evidence archive.
Validate commit identity with `validate_release_ci.py`,
`validate_cudanav_ros_ci.py` and `validate_systems_paper_archive.py`; do not reuse
evidence from a different commit. A successful manuscript-only job is not a
ready systems artifact: retain the independently validated release archive and
its SHA-256 sidecar, with any partial/blocked claims explicitly represented.

Download `cudarobotics-wheels` and `cudarobotics-manylinux-wheels` into a clean
release staging directory, then run:

```bash
python scripts/verify_python_release_artifacts.py \
  --dist-dir build/release_v0.4.0/publish \
  --json build/release_v0.4.0/python_artifacts.json --require-clean
```

Require the 0.4.0 sdist and CPython 3.10 / 3.12 manylinux wheels, all bound to the
target source provenance. Record SHA-256 and size before upload.

## Publish only after gates pass

1. Create annotated `v0.4.0` at the validated commit; never tag an unvalidated
   candidate or move an existing tag.
2. Push the tag and monitor the tag-triggered Docker workflow. Record its
   outcome without implying a physical-GPU runtime test.
3. Create the GitHub release from the notes and attach verified distribution
   files and commit-bound evidence. Do not mark incomplete assets as published.
4. Re-download assets into a new directory, verify byte counts and SHA-256, then
   independently reopen Python archives and validate evidence/checksum files.
5. Confirm tag identity, non-draft/non-prerelease status and working tag-pinned
   onboarding links.
6. Only then advance published-version declarations, wheel-selector tests and
   public installation/documentation links to v0.4.0 in a follow-up docs commit.

Without the staged exception above, queued, failed or missing gates keep the
candidate untagged. With the exception, report those blockers and never announce
binary distribution as complete merely because the source release is public.
